# 1. PROBLEM

AI coding tools (Cursor, Lovable, v0, Claude Code, Bolt) generate websites that look the same. The pattern is documented and named: **AI slop**. Inter font everywhere, purple-to-blue gradients, rounded-2xl on every card, three-column feature grids, "Build the future" hero copy, generic stock photography. Every output could belong to any company in any industry.

The cause is well understood: large language models default to the statistical mean of their training data. The most common patterns dominate generation. The result is aesthetic monoculture — what designers call "distributional convergence."

The cost is measurable. AI Slop sites have 91% lower conversion rates than quality inventory (per published research). Search engines like Google AI Overviews and Perplexity less frequently cite content that "sounds identical to thousands of other pages." Distinctive design correlates with distinctive market position; AI defaults strip both.

**The user-facing problem:** A vibe coder in Cursor types "make me a luxury hotel landing page." The output looks like every other landing page Cursor has ever produced. The user can either spend hours art-directing the AI (which defeats the speed benefit) or accept the slop (which defeats the quality bar).

**The systemic problem:** No structured design vocabulary exists that AI tools can route against. Existing solutions like `awesome-claude-design` and `getdesign.md` are static markdown files describing single brands — they don't compose, don't handle multi-axis briefs, and don't help with the *combinatorial* problem that makes design coherent.

**The thesis:** If AI-generated websites look the same because models default to the safe-mean of their training data, the fix is to give models access to *better* training data at runtime — curated, structured, opinionated — through a protocol they can already speak. That protocol is MCP.

# 2. SOLUTION

Palate is an open-source MCP server that exposes a structured design vocabulary as queryable context. AI coding tools call Palate during generation. Palate returns a card containing the right combination of design decisions across eight independent axes (layout, typography, color, component, motion, imagery, density, voice, reading-pattern). The AI tool uses the card to make better design decisions than it would default to.

The system has three components:

**Component 1 — The corpus.** Curated markdown documents defining 77 grammars across 8 axes, plus a derived JSON file containing current brand fingerprints. The hybrid model: structural grammars curated through GitHub PR review; brand exemplars derived through a periodic scraper. Source of truth split: interpretation work stays human, observation work gets automated.

**Component 2 — The MCP server.** Implements the Model Context Protocol with five tool primitives (route, route_multi, validate, list_canonical, get_brand_fingerprint), reads the corpus at startup, and runs a five-stage routing pipeline at each request. Returns cards conforming to the schema in the Compatibility Model document.

**Component 3 — The re-derivation worker.** A separate batch job that runs monthly. Visits ~70 canonical brand URLs, captures screenshots and computed CSS, extracts visual fingerprints (color tokens, typography, spacing, radii, shadows), runs voice analysis on copy, compares to existing fingerprints, flags drift, commits updated fingerprints to the corpus.

The user experience: a vibe coder in Cursor types a brief. Cursor (which has Palate registered as an MCP server) calls `palate.route(brief)`. Palate returns a card. Cursor uses the card's tokens, component recipes, voice guidelines, and anti-patterns to generate code that resists AI defaults. The output is a website that fits the brief's register rather than the AI default.

**What's specifically out of scope:** Palate does not generate code. Palate does not generate copy. Palate does not generate images. Palate provides *design context*; the consuming AI tool does the actual generation. This boundary is critical and must not blur during implementation.

# 3. USER STORIES

Stories are numbered. The "actor" is the consuming AI tool (Cursor, Lovable, v0, Claude Code, Bolt) unless specified otherwise. End users (vibe coders) interact with Palate indirectly through the AI tool's interface.

## Primary routing flow

1. As an AI tool, I want to send a natural-language brief to Palate and receive a structured design card, so that I can generate code aligned to the right register.

2. As an AI tool, I want the design card to include design tokens (colors, typography, spacing, radii, motion timings), so that I can drop them directly into CSS variables or Tailwind config without translation.

3. As an AI tool, I want the design card to include component recipes (button variants, card patterns, navigation patterns), so that I generate components that match the chosen grammar instead of falling back to my defaults.

4. As an AI tool, I want the design card to include voice guidelines (do-use phrases, do-not-use phrases, dimensional coordinates), so that copy I generate matches the brand register instead of defaulting to AI-coded boilerplate ("delve, unleash, unlock, empower," "Build the future of X").

5. As an AI tool, I want the design card to include anti-patterns specific to the chosen combination, so that I can detect and avoid AI defaults (rounded-2xl on everything, Lucide icons, Inter font) when they would conflict with the chosen register.

6. As an AI tool, I want the design card to include a reduced-motion fallback specification, so that I generate accessible code without having to derive accessibility decisions myself.

## Validation flow

7. As an AI tool, I want to send an explicit axis combination to Palate and receive a coherence verdict, so that I can detect broken combinations before generating code that would feel wrong.

8. As an AI tool, I want validation failures to include suggested corrections, so that I can route the user toward a coherent combination rather than just refusing the request.

## Listing and discovery flow

9. As an AI tool, I want to list the 15 canonical combinations Palate knows about, so that I can present them as starting points to users who don't have a brief in mind yet.

10. As an AI tool, I want to fetch the current brand fingerprint for a named brand, so that I can use up-to-date interpretation rather than my training data's snapshot of how that brand looked years ago.

## Multi-page composition flow

11. As an AI tool, I want to send multiple briefs (one per page of a multi-page site) and receive cards that maintain consistency across pages, so that the resulting site doesn't feel like nine different designers worked on it.

## Versioning flow

12. As an AI tool, I want to pin to a specific Palate spec version (e.g., v0.1.5), so that updates to brand fingerprints don't unexpectedly change interpretation for sites I've already generated.

13. As an AI tool, I want to receive metadata about which spec version produced a card, so that I can document the design decisions in version control alongside the generated code.

## Maintenance flow (operator stories)

14. As a Palate maintainer, I want to run the re-derivation worker on demand, so that I can update brand fingerprints when I notice drift before the monthly cadence runs.

15. As a Palate maintainer, I want the re-derivation worker to flag significant drift (>30% change in extracted tokens for a brand), so that I can review whether the spec's altname for that brand still matches its current expression.

16. As a Palate maintainer, I want to add a new altname (vibe phrase, brand exemplar, vernacular label, anti-vibe, or compositional intent) to an existing grammar through a markdown file edit, so that I can extend the system without code changes.

17. As a Palate maintainer, I want to add a new grammar to an axis (the Side-Scroll grammar promoted from substyle status, for example), so that the system can grow as new design vocabularies emerge.

## Contributor flow

18. As an open-source contributor, I want to file a GitHub issue for a missing brand exemplar with a canonical URL, so that the maintainer can add it to the watch list and have the worker derive its fingerprint.

19. As an open-source contributor, I want to submit a pull request adding altnames in markdown without touching code, so that I can extend the spec's coverage without needing TypeScript expertise.

20. As an open-source contributor, I want to run the routing-test validation suite locally, so that I can verify my altname additions don't accidentally break canonical routing.

## Failure mode handling

21. As an AI tool, I want a clear error response when Palate can't route a brief (the brief is too ambiguous, the requested combination is broken, etc.), so that I can ask the user a clarifying question rather than guessing.

22. As an AI tool, I want low-confidence routing results to include alternative axis combinations, so that I can surface options to the user rather than committing to a single match.

23. As an AI tool, I want Palate to gracefully degrade when the brand fingerprints file is stale or unavailable, so that routing still works (with reduced confidence) rather than failing entirely.

# 4. IMPLEMENTATION DECISIONS

This section names the load-bearing technical choices. Where a decision has been made already in the spec documents, this section points to the relevant document rather than re-deriving. Where this PRD is making a new decision, it's flagged.

## 4.1 Language and runtime

**Decision:** TypeScript on Node.js 20+.

**Reasoning:** The MCP TypeScript SDK is the most mature SDK Anthropic publishes. Most AI coding tools that consume MCP are JavaScript-coded (Cursor extensions, v0's Vercel-based stack). Open-source contributors are most likely to know TypeScript over Python or Go. Node 20+ supports the latest fetch API natively, which the re-derivation worker needs.

**Alternative considered:** Python with the MCP Python SDK. Rejected because the bulk of MCP server developers in 2026 are using TypeScript and the contributor pool is larger.

## 4.2 MCP transport

**Decision:** Both stdio and Streamable HTTP. Stdio is the default for local development and tool-tool integration; Streamable HTTP for the eventual hosted version.

**Reasoning:** Per Turn 8 Section 5.4 and the MCP architecture docs. Stdio gives optimal performance for local tools (Cursor, Claude Code on user's machine); Streamable HTTP enables the hosted Palate-as-a-service that v0.2 may offer.

**v0.1 implementation note:** Build the stdio transport first. HTTP transport gets stubbed but not productionized.

## 4.3 Corpus storage format

**Decision:** Markdown for curated content (grammars, altnames, compatibility model). JSON for derived content (brand fingerprints, computed routing tables).

**Reasoning:** Per the maintenance architecture in Turn 8 Section 7. Markdown is human-editable and PR-reviewable; JSON is machine-generated and machine-consumed. The two formats have different update cadences (curated: human-paced; derived: monthly automated) and different review processes (curated: PR review; derived: drift-flagging).

**v0.1 implementation note:** The MCP server reads markdown at startup and parses it into in-memory structures. Re-parsing happens on file change in development; on restart in production.

## 4.4 Markdown parsing strategy

**Decision (new in this PRD):** Use a structured-markdown parser (`remark` ecosystem) with custom plugins to extract grammar definitions, altname blocks, and compatibility rules into typed TypeScript objects.

**Reasoning:** The grammar documents have consistent structure — heading hierarchy maps to grammar/substyle nesting, specific section titles ("Vibes," "Brand exemplars") map to altname buckets. A parser can extract this structure without requiring the markdown to be reformatted into something less human-readable.

**Open question for Claude Code:** Is `remark` the right choice, or should we use a simpler regex-based parser given how predictable the markdown structure is? Surface this decision after attempting the implementation; the simpler approach may suffice if the markdown structure stays disciplined.

## 4.5 Routing engine

**Decision:** Implement the five-stage routing pipeline from Turn 8 Section 5.1. Each stage is a separate TypeScript function with a typed input/output contract. The stages compose into a single `route(brief: string): Card` entrypoint.

**Reasoning:** The pipeline is already specified. The implementation is glue.

**Specific stage decisions:**

- **Stage 1 (Extract Signals):** Use Claude API (claude-sonnet-4-7 or whichever current model the user prefers) for signal extraction. The brief is short; the LLM call is cheap; the extraction quality matters more than latency.
- **Stage 2 (Bucket Match):** String-matching against altname blocks, with confidence weights from Turn 8 Section 5.2 (brand exemplar 0.9, vernacular 0.7, anti-vibe 0.8 inverted, vibe 0.6, intent 0.5).
- **Stage 3 (Confidence per Axis):** Aggregate signals per axis, return ranked candidates.
- **Stage 4 (Coherence Check):** Match candidate combination against the 22 broken combinations table. Match against the 15 canonical combinations table. Return verdict.
- **Stage 5 (Conflict Resolution):** If the coherence check passes, return the combination. If not, apply the resolution strategies from Turn 8 Section 5.1 (override, snap-to-canonical, surface-conflict).

**v0.1 implementation note:** Start with the simplest possible Stage 1 — direct LLM call extracting signals into a typed object. Don't over-engineer the prompt. Iterate on the prompt during the validation-suite phase, where real briefs will surface what the LLM gets wrong.

## 4.6 LLM integration for Stage 1 signal extraction

**Decision (new in this PRD):** The MCP server requires an Anthropic API key as a configuration parameter. The signal-extraction stage uses Claude. The server documents this dependency clearly; users running Palate provide their own key.

**Reasoning:** Signal extraction needs LLM-grade understanding of natural language; rule-based parsers can't reliably distinguish "I want it to feel like Stripe" from "I'm building a payment processor like Stripe" (which route to different combinations). Anthropic's API is the most natural choice for an MCP server in the Anthropic ecosystem.

**Cost mitigation:** The signal extraction call is cheap (small input, small output). Routing should average under $0.001 per call at v0.1's expected volume. The MCP server caches signal extractions by brief hash to avoid re-running on identical briefs.

**Open question for Claude Code:** Should v0.1 also support OpenAI or open-source LLM providers for signal extraction? My recommendation is no — Anthropic-only for v0.1 simplicity, multi-provider for v0.2. But surface this if the implementation reveals the LLM call is hot enough that vendor lock-in matters.

## 4.7 Card schema

**Decision:** Per Turn 8 Section 8. The schema is fully specified there. Implementation is conversion of TypeScript interfaces from the schema, plus a card builder that populates the schema from a routed axis combination.

**Reasoning:** The schema was designed in the spec phase. Don't redesign it here.

**v0.1 implementation note:** The card schema is large (~30 fields). Implement it incrementally — start with the axis combination, add tokens, add component recipes, add voice guidelines, add anti-patterns. Each layer can ship independently.

## 4.8 Re-derivation worker architecture

**Decision:** Separate Node.js process from the MCP server. Runs on a schedule (cron in v0.1, GitHub Actions for production). Uses Playwright for browser automation, captures screenshots and computed CSS, runs visual fingerprint extraction and voice analysis, writes updated `brand-fingerprints.json` and a drift report.

**Reasoning:** Per Turn 8 Section 7. The worker is operationally separate from the runtime server — it doesn't share request/response cycles, doesn't share authentication concerns, doesn't need the same uptime guarantees.

**v0.1 implementation note:** Build the worker AFTER the MCP server is functional. Initial brand fingerprints can be hand-populated for v0.1.0 ship; the worker keeps them fresh starting v0.1.1.

## 4.9 Visual fingerprint extraction

**Decision (new in this PRD):** For each brand watch URL, the worker captures:
- Top 8 colors by usage frequency (extracted from rendered screenshot via color quantization)
- Typography fingerprint: computed `font-family` values from CSS, weight distribution, primary type scale (extracted from headings vs body text)
- Spacing distribution: most common padding/margin values across rendered components
- Border-radius distribution: histogram of border-radius values
- Shadow usage: count and intensity of box-shadow declarations

**Reasoning:** These five signals are sufficient to detect when a brand has visually drifted from its altname description. Smaller fingerprint = less storage, simpler comparison, fewer false-positive drift flags.

**Open question for Claude Code:** Color quantization is sensitive to image format and JPEG compression. The worker should screenshot in PNG and use a deterministic quantization algorithm (k-means with fixed seed). Verify this produces stable output across runs.

## 4.10 Voice fingerprint extraction

**Decision (new in this PRD):** For each brand watch URL, the worker extracts the headline + first 200 words of body copy. It runs the text through a Claude API call that scores the six voice dimensions (humor, formality, respectfulness, enthusiasm, rhythm, vocabulary) on a 0-10 scale and classifies to the nearest of the 9 voice profiles.

**Reasoning:** Voice can't be detected with rule-based analysis. Per Turn 6, the dimensional framework is the working representation; using Claude to score copy against it is the natural implementation.

**Cost mitigation:** Voice extraction runs once per brand per worker run (monthly), so 70 brands × 12 months = 840 calls per year. Negligible cost.

## 4.11 Routing test validation suite

**Decision:** Build the validation suite *first*, before the MCP server. Per Turn 9 Section 10.

**Reasoning:** The test suite is the executable form of the spec. Writing it surfaces gaps in the spec before they get baked into server code. It also gives the MCP server a clear contract to implement against.

**v0.1 specific tests required:**

1. **Canonical routing tests.** For each of the 15 canonical combinations, write at least 3 sample briefs that should route to that combination. Total: 45+ briefs. Each brief includes expected output (axis combination, expected confidence range). The test asserts the routing engine produces the expected combination.

2. **Broken combination detection tests.** For each of the 22 broken combinations, write a test that submits the broken pair and asserts the routing engine flags it as broken (either rejecting outright or resolving via Stage 5).

3. **Novel-but-coherent tests.** Write 10-15 briefs that should route to combinations not in the canonical list. Assert the routing engine returns coherent results with confidence below 1.0 (signaling novel rather than canonical).

4. **Anti-vibe routing tests.** Write briefs that include strong anti-vibe signals ("not SaaS-y," "no Inter everywhere"). Assert the routing engine excludes the negated grammars.

5. **Failure mode tests.** Write briefs that should fail routing (too ambiguous, contradictory, malformed). Assert the routing engine returns a clean error rather than guessing.

**Total expected test count:** 80-120 tests. This is the v0.1 quality bar.

## 4.12 Versioning

**Decision:** Semantic versioning on the spec corpus, not just on the server code. The MCP server takes a `palate_version` config parameter; defaults to latest. Brand fingerprints carry version metadata; the server can serve different versions of the corpus to different clients.

**Reasoning:** Per Turn 8 Section 7.3. Users pinning to v0.1.5 see the May 2026 spec; users on v0.1.9 see updated brand fingerprints. This protects against unexpected drift breaking already-generated sites.

**v0.1 implementation note:** Version pinning can be stubbed for v0.1.0 ship (every request returns the latest). Real version pinning becomes important when multiple corpus versions exist, which won't be until v0.1.5+.

# 5. TESTING DECISIONS

Testing scope: external behavior only. We test what the routing engine produces, not how it produces it. We test that the MCP server returns valid cards, not how it parses markdown.

## 5.1 Unit testing

**Out of scope:** No unit tests of internal helpers, parsers, or scoring functions. These get refactored frequently during v0.1 stabilization; pinning them down with unit tests adds maintenance burden without catching real bugs.

**In scope:** Unit tests for the public API of each module — the routing engine's `route(brief)` function, the corpus loader's `load(path)` function, the card builder's `build(combination)` function. Module-level contracts; not implementation-level details.

## 5.2 Integration testing

**The validation suite is the integration test layer.** Per 4.11 above. 80-120 tests covering canonical routing, broken combinations, novel-but-coherent, anti-vibes, and failure modes.

The validation suite runs:
- On every PR to the spec (even markdown-only changes)
- On every PR to the MCP server code
- On a schedule (daily) against the live spec to detect drift over time

## 5.3 End-to-end testing

**v0.1 scope:** Manual testing only. After the validation suite passes, manually test with at least Claude Code and Cursor — submit briefs through the MCP integration, verify the AI tool's output reflects the card.

**v0.2 scope:** Automated end-to-end testing where Palate routes briefs and a separate evaluator verifies that AI-generated output (from Claude or another LLM) actually conforms to the card. This requires more infrastructure than v0.1 should commit to.

## 5.4 Re-derivation worker testing

**The worker is harder to test than the routing engine** because it depends on live websites that change. Test strategy:

- **Snapshot tests** for the visual fingerprint extraction logic. Provide a known PNG, assert color quantization produces expected output. Tests the algorithm, not the live web.
- **Mock-website tests** for the Playwright integration. Spin up a known HTML/CSS test page locally, run the worker against it, assert fingerprint output matches expected.
- **Integration tests** against a small set of stable brand URLs (Wikipedia, MDN, etc.) that change rarely. Run weekly to detect worker drift; alert on unexpected output changes.

**Out of scope for v0.1:** End-to-end testing of the worker against the actual brand watch list. Too much variance; will ship with manual review of worker output before each spec version release.

## 5.5 Prior art for testing

The mattpocock PRD format calls for citing prior art for testing decisions. The most applicable references:

- **MCP Inspector** (the official Anthropic tool) — Palate should be testable via MCP Inspector for protocol-level verification.
- **vitest** for the TypeScript test runner — modern, fast, good developer experience.
- **Playwright** for the browser automation in the re-derivation worker — Microsoft's tool, well-maintained, used widely for design system scrapers.

# 6. OUT OF SCOPE FOR v0.1

Things that have been considered and explicitly deferred. If Claude Code finds itself building these, stop and surface the question.

## 6.1 Code generation
Palate provides design context. It does not generate HTML, CSS, JSX, or any other code. The consuming AI tool generates the code using Palate's card as input.

## 6.2 Copy generation
Palate provides voice guidelines (do-use phrases, do-not-use phrases, dimensional coordinates). It does not generate copy. The consuming AI tool generates copy using Palate's voice guidelines as input.

## 6.3 Image generation
Palate provides imagery grammar guidance (Editorial Photography, 3D Render, etc.) and anti-patterns (no AI-generated illustrations, no stock photo clichés). It does not generate images. The consuming AI tool sources or generates images guided by Palate's grammar.

## 6.4 Multi-page consistency
v0.1 ships per-page card routing. v0.2 may add multi-page composition where the cards must stay consistent across pages of the same site. Don't build this for v0.1.

## 6.5 RTL language support
v0.1 ships left-to-right reading patterns only. RTL language reading-pattern grammars are documented in the spec but not implemented for v0.1. Don't build them.

## 6.6 Embedding-based altname retrieval
v0.1 uses LLM interpretation against curated altname blocks. v0.2 may add vector embedding retrieval for arbitrary phrasings. Don't build vector storage or embedding pipelines for v0.1.

## 6.7 The brand observatory dashboard
A visualization tool for inspecting brand fingerprint drift. Mentioned in the maintenance architecture as a v0.2 feature. Don't build it for v0.1.

## 6.8 Per-vertical extension grammars
Hospitality-specific layout substyles, fintech-specific component substyles, etc. v0.1 keeps grammars general. Don't add vertical-specific extensions.

## 6.9 The Side-Scroll layout grammar
Currently a substyle within Catalog. Documented in the spec as a candidate for promotion to its own grammar in v0.2. Don't promote it for v0.1.

## 6.10 OAuth and authentication
v0.1 ships with no authentication — public usage is anonymous. OAuth becomes load-bearing if v0.2 adds personalization or rate-limited tiers. Don't implement auth for v0.1.

## 6.11 Hosted Palate-as-a-service
v0.1 is library-only. Users install it locally and configure their AI tools to use it. Hosted service comes in v0.2 if demand justifies operational cost.

## 6.12 Mission-Earnest and Aspirational-Lifestyle voice profiles
Considered for v0.1 but didn't pass the routing test. Documented as v0.2 candidates if accumulated brief data justifies. Don't add them for v0.1.

# 7. BUILD ORDER

The four phases of v0.1 implementation, in order. Each phase has a clear done-criterion. Don't move to phase N+1 until phase N is complete.

**Done when:** All 80+ validation tests pass. The `route(brief)` function reliably produces correct combinations for canonical briefs.

## Phase 3: Card generator and MCP server (estimated: 2-3 days)

**Tasks:**
- Build the card generator — populates the schema from Turn 8 Section 8 from a routed axis combination.

- Stub HTTP transport (don't productionize).
- Manual integration test with Claude Code: register Palate as an MCP server, submit briefs, verify cards return correctly.
- Manual integration test with Cursor (or another consumer the user has access to).

**Done when:** A real AI tool (Claude Code minimum) can call Palate via MCP and receive valid cards. Manual review of 5+ generated outputs confirms cards drive the AI tool away from default slop.

## Phase 4: Re-derivation worker (estimated: 2-3 days)

**Tasks:**
- Build the Playwright-based scraper.
- Build visual fingerprint extraction (color quantization, typography extraction, spacing/radius/shadow analysis).

- Build the drift report generator — markdown summary of changes for human review.
- Set up GitHub Actions workflow to run the worker monthly.
- Run the worker against the full 70-brand watch list. Hand-review the output. Update `brand-fingerprints.json` with verified data.

**Done when:** Worker runs end-to-end against the full watch list, produces a sane drift report, commits updated fingerprints. Monthly automated cadence is set up.

## Phase 5: Documentation and v0.1.0 release (estimated: 1-2 days)

**Tasks:**
- Write README.md per Turn 9 Section 9.
- Write CONTRIBUTING.md covering the curated/derived split per Turn 9.
- Write `docs/architecture.md`, `docs/grammar-authoring.md`, `docs/altname-curation.md`, `docs/brand-fingerprint-format.md`, `docs/mcp-integration.md`.
- Write the example briefs directory (20-30 examples covering canonicals + novel-but-coherent).
- Tag v0.1.0 on the repository.
- Publish the MCP server package (npm or wherever MCP servers register).

**Done when:** A new user can clone the repo, install dependencies, register Palate in their AI tool, and successfully route a brief — all from documentation alone, no help from the maintainer.

**Total estimated v0.1 build time: 9-13 working days.**

This is an estimate, not a commitment. Real estimate-vs-actual variance for software is large. Don't take this number to a stakeholder as a deadline.

# 8. FURTHER NOTES

## 8.1 Things I'm uncertain about

Honest flags where I don't have enough context to make a clean decision:

**The right way to integrate Palate with Cursor specifically.** Cursor's MCP integration has been evolving; the exact configuration steps vibe coders need to add Palate to their Cursor setup may have changed since the documentation I've consulted. Phase 3's "manual integration test with Cursor" is where this gets verified; the README's Cursor-specific instructions should be written *after* that integration is verified, not before.

**Whether Stage 1 (Extract Signals) should be one Claude call or multiple.** I've specified one call. Reality may require splitting into multiple — one for brand exemplars, one for vibe phrases, one for compositional intent — if the single call's output is unreliable. Iterate during Phase 2.

**The right threshold for drift detection in the re-derivation worker.** I've said >30% change in extracted tokens triggers a flag. That's a guess. Tune during Phase 4 against real worker output.

**Whether the validation suite's 80-120 test count is the right size.** Could be 40, could be 200. The right number is "enough to catch the bugs that matter" — adjust as the suite is built.

## 8.2 Risks I want to surface explicitly

**Risk 1: The signal extraction LLM call is slower than expected.** Each routing request takes 1-2 seconds for the Claude call. For interactive use in an AI coding tool, this may feel sluggish. Mitigation: cache aggressively by brief hash, return cached results when the same brief appears.

**Risk 2: The re-derivation worker breaks on website changes.** Brand sites change their structure. CSS classes get obfuscated by build systems. The worker may produce nonsense output for some brands within months. Mitigation: the worker's drift report is human-reviewed; bad output gets flagged, brand watch list gets updated to remove broken targets or use alternative URLs.

**Risk 3: Vibe coders don't use Palate even when it's available.** The product depends on AI tools deciding to call Palate. If Cursor's defaults work "well enough" without Palate, vibe coders won't integrate it. Mitigation: the v0.1 documentation needs to make Palate's value visceral — side-by-side comparisons of slop vs Palate-routed output, before/after screenshots, etc.

**Risk 4: The spec has bugs that only surface during real usage.** Eight axes × hundreds of grammars and substyles × thousands of altname entries — there will be inconsistencies. Mitigation: ship v0.1 publicly even with known imperfections; let real briefs surface the gaps; iterate.

**Risk 5: The legal status of brand exemplar names.** Listing "Aman" or "Hermès" as an altname pointing to a design pattern is referencing the brand for descriptive purposes, which is legally fine. But the brand fingerprints — periodic screenshots of the actual sites — exist in a fuzzier zone. Mitigation: the worker stores numerical fingerprints (color tokens, spacing values) rather than the screenshots themselves. Screenshots are computed and discarded; only the derived data persists.

## 8.3 Submitting this PRD as a GitHub issue

When the repository exists, this PRD should be submitted as a GitHub issue or pinned discussion. Title: `v0.1 Implementation Plan`. Reference all nine spec documents in the issue body. Each phase becomes a milestone; tasks within phases become individual issues.

This makes the build-order explicit, lets contributors find work to pick up, and creates a paper trail for why decisions were made the way they were.

## 8.4 What success looks like at v0.1.0

The minimum viable shape of "v0.1.0 ships":

- Repository public on GitHub.
- README.md explains what Palate is, how to install, how to integrate with at least Claude Code and Cursor.
- All 15 canonical combinations are routable from natural-language briefs in the validation suite.

That last bullet is the real test. Architecture and tests can pass without the system being useful. External validation by a third-party user is the truest signal.
